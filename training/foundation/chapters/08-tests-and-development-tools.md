# 08：测试与开发检查工具

建议时间：106–112 分钟。

## 学习目标

- 区分格式化、代码检查、类型检查和测试各自回答的问题。
- 知道一次检查通过不能替代其他检查，也不能证明程序不存在缺陷。
- 理解 CI 是在约定环境中自动执行已有检查的机制，而不是新的代码质量标准。

## 一张对照表

| 检查 | 主要回答的问题 | Python 示例 | Rust 示例 |
|---|---|---|---|
| 格式化 | 代码排版是否符合统一规则？ | Ruff formatter | `cargo fmt` |
| 代码与静态检查 | 是否存在约定禁止或工具能够发现的问题？ | Ruff check | `cargo clippy` |
| 类型检查 | 类型使用是否与声明和推断一致？ | Pyright | Rust 编译器的类型检查 |
| 测试 | 给定输入时，实际行为是否符合断言？ | pytest | `cargo test` |

工具边界比具体命令更重要：格式化通常会改写排版；静态检查和类型检查主要分析代码；测试会运行被测行为。不同工具可能有少量能力重叠，但不能视为同一个步骤。

## 穿插演示

在 [`demos/foundation/`](../../../demos/foundation/) 中准备几个彼此独立的极小问题：

1. 只违反格式规则，但仍能运行。
2. 能运行，但静态检查或类型检查给出问题。
3. 能通过静态检查，但测试断言失败。
4. 修复后由同一组命令重新检查。

演示 Python 与 Rust 两组工具名称即可，不要求候选人现场安装或记住所有命令。

## CI 的位置

```text
开发者在本地运行检查
  → 将检查命令写入项目约定
  → CI 在新的、可重复的环境中自动执行
  → 将结果反馈给开发者
```

- CI 可以帮助发现“本机能运行、换环境失败”或忘记运行检查的问题。
- CI 仍然只会执行配置中写明的步骤。
- 正式招新项目中的 CI 是扩展任务，不是两条路线的主线门槛。

## 常见误解

- “格式化工具会判断业务逻辑是否正确。”
- “静态检查一定会执行程序。”
- “测试通过就说明代码没有其他问题。”
- “CI 通过说明另一台电脑必然能够完成所有操作。”

## 过渡

> 工具给出的失败信息不是最终答案，而是定位问题的证据。最后一章讨论怎样读取这些证据并开展下一步学习。
