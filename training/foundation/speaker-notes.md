# 两小时基础课讲师备注

## 授课原则

- 每引入一个术语，都回答它解决什么问题。
- 使用“计算机开发基础”的层次关系连接章节，避免堆叠互不关联的定义。
- [`demos/foundation/`](../../demos/foundation/) 中的课堂 demo 只作为第二小时的具体练习材料，不从该项目开始课程，也不强行贯穿每个概念。
- 不假设候选人已经完成所有预备操作。
- 候选人现场操作失败时，先让其继续听课，不把课堂变成长时间个别排障。
- 明确区分“需要理解的模型”和“现在需要记住的命令”。
- Python/Rust 示例用于比较工具链，不讲解语言语法优劣。

## 需要反复强调的边界

- 代码、解释器或编译器、依赖、项目环境不是同一个对象。
- 第三方包不是引用名称后自动出现的软件；它需要取得并安装到正确环境。
- 同一个包的不同版本可能具有不同接口和行为；“已经安装”不等于“版本匹配”。
- 一个直接依赖可能继续依赖其他包，锁文件记录的不只是候选人手动选择的包。
- 编辑器只是修改文本的工具，不是程序运行环境本身。
- Git 与 GitHub 不同，commit 与 push 不同。
- 测试、格式化、静态规则和类型检查不能互相替代。
- 报错是当前模型与实际状态不一致的证据，不是单纯的失败标志。
- AI 输出必须通过文档、运行、测试或最小实验验证。

## 时间控制

- 开场不重新讲 intro 内容。
- 操作系统、shell、文件和路径部分只覆盖后续开发需要的概念，但必须给候选人实际操作机会。
- 不在现场解决少数人的复杂安装问题。
- 路线交接必须在 118 分钟开始，不由前面章节挤占。
- 候选人的延伸问题记录到课后答疑，不在课堂展开专业细节。

## 常见误解清单

- “打开终端后默认就在项目目录。”
- “终端、shell、命令行和操作系统是同一个东西。”
- “文件扩展名决定了文件内部格式。”
- “所有 Word 文档都是 ZIP 包。”
- “在源码中写出包名后，包就自动存在。”
- “代码文件存在就一定能运行。”
- “下载了依赖声明就等于安装了依赖。”
- “虚拟环境需要上传到 GitHub。”
- “commit 就是上传。”
- “测试通过就说明代码没有其他问题。”
- “静态检查工具运行了代码。”
- “AI 给出的命令能执行就一定安全、正确。”
- “操作系统通常不允许同一个可执行文件启动多个进程。”
