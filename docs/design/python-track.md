# Python 起点路线

Python 路线面向刚学完变量、分支、循环、函数等基础语法的候选人，以较低的语法负担和可运行的起始仓库降低上手难度。重点观察阅读已有代码、扩展功能、验证修改和处理问题的能力，不要求从空目录独立搭建项目。

尚未掌握基础语法者应先补学，再进入项目；这不是参加两小时基础课的前提。

## 项目：本地客户端—服务端工具服务

出题方提供已有基本功能的 Python 起始仓库。选择本项目的候选人通过 GitHub 模板创建个人仓库，在其上逐步扩展客户端和服务端，项目周期约一个月。起始代码、任务说明和验证材料共同构成本项目的完整入口。

客户端负责接收用户输入、发送请求和显示结果；服务端负责处理请求并返回结果。候选人先接入已有的服务端功能，再逐步实现需要两端配合的新功能。

项目只在本机通信。通信层完整提供，主线采用同步处理；候选人需要理解请求—响应格式和调用关系，主要修改业务处理与客户端功能，不要求实现底层连接读写、消息分帧、异步并发、数据库或持久化。

### 起始仓库已有能力

- 可直接运行的服务端和文字菜单客户端，支持连续交互。
- 两端均已支持 `ping`（确认服务可响应）和 `echo`（返回发送的内容）。
- 服务端已实现 `text_stats`，返回文本字符数和行数；客户端尚无对应入口。
- 完整的通信、JSON 消息读写、请求分发和基础错误响应。
- uv 项目配置、锁文件、pytest、Ruff、Pyright 和全部通过的起始测试。

起始框架以功能正常、测试通过的状态交付。实现结构与第三方依赖按实际需要选择，不预先限定编程范式或固定业务依赖。

## 协议边界

客户端与服务端使用 UTF-8 编码，每行传输一个完整的 JSON 消息。请求包含用于对应响应的 `id`、指定操作的 `action`，以及该操作需要的参数；响应包含对应的 `id`、表示成功与否的 `ok`，以及结果或错误信息。

同一连接内依次处理请求，每个请求对应一个响应，主线不要求并发处理。业务参数非法时返回可理解的错误，候选人须保留原有功能及错误处理能力。具体动作、输入输出和边界规则由本项目任务书定义。

## 学习阶段与主线层级

### 运行与理解起始仓库

- 使用 GitHub 模板创建个人仓库，取得代码并恢复 uv 环境。
- 运行两端、测试、格式检查、代码检查和类型检查。
- 追踪一次 `echo` 请求从客户端输入到服务端处理再到结果显示的过程。
- 理解解释器、虚拟环境、依赖清单、锁文件和本机生成内容的关系。
- 区分源码、测试、工具配置与 `.venv`、缓存等可重建内容。

环境与工具链学习直接在起始仓库中完成，不另设环境成果提交。可以每次引入一处可恢复的修改，观察格式、类型与测试报告的差异，再恢复检查通过的状态。

### 基础层：接入文本统计

服务端已支持 `text_stats`。候选人只需修改客户端，增加文本输入、请求构造、字符数和行数显示，并补充客户端相关测试。

候选人依据协议与结构导览自行定位修改位置，不提供逐函数填空步骤。已有服务端测试不能代替对客户端新增行为的验证。

### 标准层：新增数值统计

候选人在两端增加 `number_stats`：

- 客户端接受数值列表输入，构造请求并显示结果或错误。
- 服务端处理非空数值列表，返回数量、最小值、最大值和平均值。
- 对非法输入提供清晰错误；合理拆分处理逻辑。
- 补充正常、异常与边界测试，并检查原有动作仍能使用。

### 进阶层：内存键值存取

候选人在两端增加 `set/get/delete/list`，按字符串键保存和查询字符串值，处理缺失键等错误。

状态在服务端运行期间跨请求保留，重启后清空；不引入文件持久化或数据库。候选人需要验证操作顺序、状态变化及不同功能之间的影响。

### 扩展：CI

完成主要学习目标后，可以使用 GitHub Actions 在干净环境中运行 pytest、Ruff 和 Pyright。起始仓库不提供可直接复制的 CI workflow，CI 不属于录取门槛。

## 指南与验证

任务书提供行为要求、输入输出示例、验收场景和代码结构导览，不逐项指定修改文件、函数及实现步骤。

起始测试覆盖已有动作、通信层和基础错误处理。出题方为新增功能提供少量正常场景自查用例；候选人自行补充异常与边界测试。验收依据公开规则，不通过隐藏需求增加难度。

## 工程基础、仓库与评价

候选人需要学习 [Git、GitHub 和适用 Windows 候选人的 WSL2 基础任务](./common-foundations.md)。编程项目不要求在 WSL2 中完成。

个人仓库保留起始代码，包含源码、测试、`pyproject.toml`、锁文件、必要的 Python 版本信息、`.gitignore` 和 README，不提交 `.venv`、缓存或生成内容。

README 应说明环境恢复、运行与检查方式，并区分起始仓库已有功能和本人新增功能。保留从初始版本开始的自然提交历史，使用简短的 `PROGRESS.md` 或等效材料记录三个轻量检查点：问题、验证方法和后续计划，不要求日报。

评价重点是候选人对继承代码和个人修改的理解、问题分析及学习迭代。起始代码的已有能力不计为个人新增成果；未完成全部层级，或检查尚有问题，不自动淘汰。
