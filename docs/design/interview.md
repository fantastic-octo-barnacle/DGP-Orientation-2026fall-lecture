# 最终面试设计

面试用于核验候选人的理解程度、学习过程、解决问题方式和可靠性。它不以项目演示效果为唯一依据，不设置统一算法笔试，也不要求复杂的现场编程。

## 建议结构

每名候选人约 40 分钟：

1. 项目与当前状态介绍，约 5 分钟。
2. 学习过程复盘，约 8 分钟。
3. 自己项目的代码和工程配置追问，约 10 分钟。
4. 路线相关的概念与故障场景，约 7 分钟。
5. 基本命令行操作，约 8 分钟。
6. 后续培养和时间投入沟通，约 2 分钟。

面试时间可以根据候选人的项目进度调整，但评委应覆盖学习、理解、问题分析和可靠性，而不是只追问完成的功能。

## 现场规则

- 现场通常不允许搜索或使用 AI。
- 一般不提出需要长时间探索、查资料或比较方案的开放问题。
- 不要求候选人现场实现复杂功能。
- 对于增加筛选条件、修复异常或解决异步阻塞等问题，候选人描述实现思路、注意事项和验证方法即可。
- 实操仅考查与任务相关的基本命令行操作。
- 命令行实操可以使用候选人熟悉的 shell；允许查看命令自身的 `--help`，但不允许联网搜索。
- 项目未完成时，仍然围绕现有代码、故障判断和下一步计划展开。

## 分支式题树

面试只准备少量固定题树，不以大量等价题防止泄题。每棵题树包含：

- 主问题。
- 回答清楚后的深入追问。
- 回答不完整时的提示问题。
- 仍无法回答时的基础降级题。
- 各分支的可接受答案范围和关键误解。

每名候选人的面试包含通用基础题、路线题、根据本人仓库选择的项目题，以及一段基本命令行实操。公开考查范围和示例题型，不把题目泄露风险作为主要设计约束。

## 通用追问方向

- 最困难的问题是什么，如何缩小范围？
- 使用了哪些资料，怎样判断资料可信或适用？
- AI 或他人给出的建议如何验证？
- 收到反馈后做了什么调整？
- 哪些代码或配置仍不理解？
- 如果再给一天时间，下一步会做什么，如何验证完成？

## Python 路线重点

- CPython、解释器、虚拟环境、依赖与 uv 的关系。
- clone 后没有 `.venv`，为什么仍能恢复项目。
- `pyproject.toml`、锁文件和 `.gitignore` 中的内容为何不同。
- Ruff、Pyright 和 pytest 分别能发现什么问题。
- Windows 与 WSL2 中的软件为何彼此独立。
- 日志解析、验证、错误隔离、筛选和测试的实现思路。

## Rust 路线重点

- Cargo 项目、依赖、构建产物、锁文件和环境复现。
- `cargo fmt`、`cargo check`、`cargo clippy` 和 `cargo test` 的不同作用。
- 所有权、借用、字符串、结构体、枚举和 `Result` 等项目中实际使用的语言概念。
- Serde 数据模型、错误处理和客户端—服务端项目结构。
- 已进入 Tokio 层级者，再考查异步任务、异步等待和阻塞操作。
- 参考程序可以用于项目追问，但不把 TCP 底层细节作为固定知识题。

## 命令行实操范围

实操使用预先准备的临时目录或小仓库，不直接操作候选人的正式项目。范围应限于候选人任务中实际接触过的基础操作，例如：

- 查看当前目录和目录内容。
- 创建、复制、移动或检查一个普通文件。
- 查看 Git 状态、差异和历史。
- 运行项目、测试或静态检查命令。
- 判断当前使用的 Python 解释器或 Rust 构建结果位置。

不通过冷门命令、打字速度或 shell 技巧区分候选人。

## 诚信核验

项目期间允许搜索、AI、讨论和求助。面试通过解释关键代码、重现思路和回答具体追问判断成果是否真正属于候选人的理解范围。使用 AI 本身不扣分；隐瞒复制、代做或冒充原创属于红线。

早期问题草案见[内部面试题库](../drafts/interview-question-bank.md)。这些题目用于验证题树形式，不是最终定稿；正式面试将在项目 spec 完成后重新设计。
