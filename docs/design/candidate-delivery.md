# 候选人交付仓库需求记录

记录日期：2026-09-18。

本文记录面向候选人的独立交付仓库需要包含什么、如何组织，以及何时算可发布。当前已获授权实施：创建 private 模板仓库，编写候选人材料、基线和验证工具；公开发布另行安排。

## 目标与适用范围

候选人从一个统一入口了解招新项目，完成共通基础任务，选择一个编程项目，取得对应基线代码，并按公开要求实现、验证和提交个人成果。

所有候选人交付材料放在一个新 Git 仓库中。当前仓库继续保存内部设计、讨论草案和评审材料。新仓库不要求候选人返回内部设计仓库查找完成任务所需的信息。

编程项目为 Python、Rust 二选一。项目详细说明各自独立描述目标、协议和要求，不依赖另一项目文档。两项目采用通用协议，相同动作必须互通，由唯一的 Rust 参考程序覆盖全部动作；候选人仍只实现所选项目范围。跨项目的介绍与选择建议只放在统一入口。

## 设计依据与版本

- 本轮交付以已经确认的最新方案为依据，不机械复制当前工作分支中的旧文件。
- Python 采用基于客户端—服务端基线扩展的设计，来源为提交 `6851650` 的 [Python 路线文档](https://github.com/fantastic-octo-barnacle/DGP-Orientation-2026fall-training/blob/6851650ddbbdd2d9cb8c9fba6428246982663334/docs/design/python-track.md)。记录时 PR #1 尚未合并，当前分支中的日志检查器和独立环境 Demo 文档不是本轮交付依据。
- Rust 采用三个独立 Cargo 项目的框架扩展设计，来源为提交 `de9e4e3`；见 [Rust 路线](./rust-track.md)、[起始仓库](../drafts/projects/rust-starter.md)、[协议](../drafts/projects/rust-protocol.md)及[参考程序规范](../drafts/projects/rust-reference-program.md)。PR #2 已合并。
- 共通线依据[共同基础任务](./common-foundations.md)、[Git/GitHub 草案](../drafts/projects/git-github.md)和 [WSL2 草案](../drafts/projects/wsl2.md)。
- 具体协议限值、错误语义和时间参数中仍属草案的部分，需要在候选人版发布前定稿，并与代码和测试一致。

以上版本记录供维护者追溯，不要求将 PR 历史和旧方案说明复制给候选人。

## 五项交付物

### 1. 首读说明

新仓库根目录的 `README.md` 是候选人最先阅读的材料，至少包含：

- 项目的目的、总体流程、预计周期和候选人承担的工作。
- 共通基础任务与二选一编程项目的关系。
- Python 与 Rust 分别做什么、适合什么起点，以及选择建议。
- Python 面向刚学完基础语法者；Rust 面向能独立编写简单程序者，不要求事先会 Rust。尚未掌握基础语法者先补学再进入项目。
- 阅读顺序：共通指引 → 所选项目任务书 → 环境与运行说明 → 基线检查 → 分层开发与自查 → 提交。
- 学习期间允许查资料、使用 AI、讨论和求助，但需理解、验证并说明来源；未完成全部层级不自动淘汰。
- 项目材料、技术成果要求与相关文档入口。活动日期、检查点时间、提交渠道和求助渠道不写入仓库，也不留占位提示，由仓库外安排。

说明应让第一次进入仓库的候选人知道现在做什么、接着读什么，不要求先理解内部设计术语。

### 2. Git/GitHub、WSL2 共通指引

共通线适用于选择任一编程项目的候选人，独立于具体语言。

- Git/GitHub：通过纯文本练习建立本地与远程仓库、提交与同步、克隆和忽略文件的工作模型；提供目标、任务、自检、官方资料方向和求助建议。
- WSL2：说明适用条件、安装与启动目标、Windows/Linux 路径与环境的区别、文件互访、进入退出及关闭环境。
- WSL2 安装任务仅适用于使用 Windows 且设备条件允许者；macOS 不设置对等安装任务。项目不强制在 WSL2 内完成。
- 已掌握的练习可跳过，不要求另交截图或练习仓库；实际工程习惯通过所选项目观察。
- 提供学习目标、概念提示和必要入口，不把指南写成所有练习和故障的逐步答案。

“两条路线都会做共通内容”不改变 WSL2 的设备适用边界。

### 3. 两个项目的候选人版详细说明

每个项目分别具备：

- 项目目标、必要知识和工具条件。
- 起始代码已有能力、候选人需要实现的能力及不要求的内容。
- 项目结构导览、环境恢复、启动、停止和检查方式。
- 各学习阶段和功能层级的目标、行为要求与验收场景。
- 自身完整的协议、输入输出示例、错误与边界规则。
- 测试方法、如何读取失败信息，以及还需候选人自行补充哪些测试。
- 交付物清单：个人源码和测试、清单与锁文件、README、自然提交历史、三个轻量过程记录。
- 如何标明基线已有功能、个人新增功能、未完成项及已知问题。
- 技术成果整理方式与可选 CI 扩展；活动安排不进入项目仓库。

任务书描述行为与验证方法，不给逐函数 TODO 或完整解法。基线启动、检查等使用说明需足够具体，不能让候选人靠猜测运行已有代码。

### 4. 可运行的项目基线代码

保留新版 Python、Rust 的完整可运行起始代码，统一放入新交付仓库。取消旧 Python 独立工具链 Demo C；环境与工具链学习直接在正式项目基线上完成，不再单独交付 Demo C 仓库或任务。

**Python 基线**：

- 一个完整 uv 项目，包含同步客户端和服务端、依赖与锁文件、pytest、Ruff、Pyright 配置。
- 两端支持 `ping/echo`，服务端已支持 `text_stats`，客户端尚未接入文本统计。
- 候选人基础层接入文本统计客户端，标准层在两端实现 `number_stats`，进阶层在两端实现内存 `set/get/delete/list`。
- 通信层完整提供；基线测试和检查通过，不故意埋 bug。

**Rust 基线**：

- 同步客户端、同步服务端、异步服务端三个独立 Cargo 项目，各有自己的清单、锁文件、源码和测试，不用 workspace，不另加共享协议 crate。
- 三个项目均支持 `ping` 及对应基础错误处理；异步服务端使用 Tokio，但初始顺序处理连接。
- 候选人实现 `echo/delay`、连续交互、完整校验和边界处理，再完善跨连接并发、超时和有界退出。
- 三个基线项目均可分别运行和检查，已有测试全部通过。

基线是候选人的开发起点，不包含新增功能的完整答案。公共测试不能在默认运行时因尚未完成后续任务而失败。

### 5. 自查测试、验收材料及说明

明确区分三种材料：

| 材料 | 用途 | 交付要求 |
|---|---|---|
| 基线测试 | 确认出题方提供的能力正常工作 | 随源码提供，初始版本全部通过 |
| 阶段自查 | 检查候选人已实现的功能 | 少量正常场景、示例数据或请求及明确的使用时机 |
| 公开验收清单 | 说明每项要求如何观察和判断 | 覆盖功能、错误、边界、回归及适用的并发和生命周期行为 |

- 每组材料注明适用阶段、运行条件、操作方式、预期结果和失败信息的含义。
- 候选人仍需编写异常与边界测试，不直接提供完整测试答案。
- 不能仅因公开自查通过就宣称已覆盖全部要求；正式检查必须依据公开任务规则，不额外引入隐藏需求。
- Rust 并发验证检查响应事件先后；超时与退出测试有可配置时间上限，避免依赖偶然调度。
- 按现行 Rust 设计保留独立可执行参考程序，配套平台版本、下载方式和校验值；它属于验证材料，不是额外候选人项目。
- 可执行参考程序可通过新仓库的 Releases 分发；仓库内保留文档和固定版本入口，不将参考实现源码或标准答案放入候选人仓库。

## 建议目录结构

以下为新仓库的建议结构，目录名可在实施时统一，但需保持“一个入口、共通线、两个独立项目”的关系。

```text
candidate-projects/
├── README.md                     # 首读：整体介绍、选择与后续入口
├── .gitignore
├── common/
│   ├── git-github.md
│   ├── wsl2.md
│   └── deliverables.md           # 技术成果与来源说明
├── projects/
│   ├── python/
│   │   ├── README.md             # 候选人任务书与运行入口
│   │   ├── protocol.md
│   │   ├── acceptance.md
│   │   ├── pyproject.toml
│   │   ├── uv.lock
│   │   ├── .python-version
│   │   ├── src/
│   │   ├── tests/                # 基线测试
│   │   └── self-check/           # 分阶段自查、数据及说明
│   └── rust/
│       ├── README.md             # 三项目任务书与分别运行的说明
│       ├── protocol.md
│       ├── acceptance.md
│       ├── client-sync/
│       │   ├── Cargo.toml
│       │   ├── Cargo.lock
│       │   ├── src/
│       │   └── tests/
│       ├── server-sync/          # 同样独立的清单、锁文件、源码和测试
│       ├── server-async/         # 同样独立的清单、锁文件、源码和测试
│       └── self-check/
├── reference/
│   └── README.md                 # 通用参考程序的版本、获取与使用
└── assets/                       # 文档必要图片等公共静态资源
```

根目录和 `projects/rust/` 不设置 Cargo workspace。选择一个项目不应要求安装另一个项目的语言工具链。自查脚本使用什么工具、如何运行，也要在所选项目内说清楚。

新仓库是统一交付来源和 GitHub 模板。候选人通过整个模板创建个人成果仓库，只修改所选项目，另一项目可以保留原样；不要求安装另一语言工具链。

## 不进入候选人仓库的内容

- 内部面试题、参考答案、评价记录、评委校准材料。
- 新增功能的完整参考实现和覆盖全部解法的测试答案。
- 设计讨论历史、未确定的备选方案和旧任务草案。
- 旧 Python 独立工具链 Demo C；其学习目标由正式项目基线承载。
- 讲师脚本和课堂演示工程；本次交付仓库聚焦正式项目，可链接已发布的学习材料。

## 完成与发布标准

1. 从根 README 可找到全部必需材料，候选人不需要访问当前内部仓库。
2. 项目目标、协议、基线行为、自查结果和验收规则一致，公开要求不留“待定”占位。
3. 在干净环境下按说明能恢复、运行和检查基线，记录实际验证的平台与工具版本。
4. Python 基线和三个 Rust 基线分别通过自身测试与开发检查；运行所选项目不依赖另一项目。
5. 阶段自查的适用时间清楚，不把未来功能未实现误报为基线故障。
6. 所有相对链接和下载入口可用，参考程序版本与协议一致，发布材料与内部材料隔离。
7. 个人仓库获取方式明确；活动日期、检查点时间、提交及求助渠道没有进入仓库。
