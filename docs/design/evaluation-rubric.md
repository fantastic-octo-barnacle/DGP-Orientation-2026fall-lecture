# 评审框架

评审用于判断候选人是否值得进入长期培养阶段。当前不设置固定数值权重，也不根据项目层级或功能数量自动排序。

## 评价维度

### 学习与迭代

观察候选人相对于自身起点的变化、吸收反馈的速度、资料使用方式，以及能否修正原有认识。

### 分析与解决问题

观察其是否能够描述现象、提出假设、缩小问题、构造验证方法，并根据结果调整下一步。

### 投入可靠性与工程习惯

观察其是否持续推进、遵守约定、及时沟通问题，并恰当使用 Git、README、测试和项目配置。

### 理解与表达

观察其能否用自己的语言解释代码、环境、工具、错误和方案选择，而不是只复述教程或工具输出。

### 项目成果

观察项目当前是否可运行、核心结果是否正确、仓库是否可理解和恢复。成果是学习证据的一部分，不构成独立录取门槛。

## 证据记录

评委应先记录事实，再给出判断。例如：

> 收到输入解析反馈后，候选人重写了验证逻辑并增加三个异常输入测试。

比下面的记录更可复核：

> 学习态度很好。

每名候选人至少由两名评委独立查看主要证据，再通过校准讨论形成结论。

## 路线校准

- Python 与 Rust 路线按不同起点观察成长，不横向比较绝对功能数量。
- 不设置路线硬配额。
- 如果最终结果明显只偏向已有基础者，应复核评委是否事实上仍按完成度排序。
- 完成高级层级不能覆盖缺乏理解、可靠性或诚信的问题。
- 未完成项目不能覆盖明确的学习进展和优秀的问题分析证据。

## 红线

- 抄袭、代做、隐瞒关键代码来源或冒充原创。
- 多次无故失联或反复违反明确约定。
- 明确拒绝反馈，或在团队协作中表现出严重不可靠行为。
- 对设备、账号或他人数据实施明显不安全的操作。

基础薄弱、表达不流畅、没有完成异步层级或项目尚未运行完整，都不是自动淘汰条件。

## 校准结果

从约 40–50 名候选人中录取约 7–8 名预备队员。评委最终回答的问题是：

> 现有证据是否表明，这名候选人值得团队投入后续长期培养资源？

具体评审表、行为锚点和通过规则留待后续设计。
