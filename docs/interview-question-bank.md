# 面试题库早期草案（内部、非最终定稿）

本文档仅供评委使用，记录框架设计阶段产生的早期题目。题目本身不是最终定稿；待正式项目 spec 完成后，将按实际教学与任务内容重新设计最终题树。

保留的形式原则是：使用少量固定题树，每棵题树根据候选人的回答进行深入追问或基础降级，不以准备大量等价题防止泄题。

## 记录方式

每道题记录以下三级状态之一：

- **理解清楚**：能够解释原因，并说明如何验证或处理。
- **部分理解**：知道操作或部分概念，但模型不完整。
- **存在关键误解**：只能背诵命令，或对环境、协议和工具作用形成错误模型。

另行记录候选人是否诚实说明不知道、能否根据追问修正认识、是否把猜测当成事实，以及能否联系自己的项目。

## 第一批概念题

### clone 后没有 `.venv`

**问题**：从 GitHub clone 下来的 Python 项目为什么通常没有 `.venv`？怎样恢复项目？

**参考要点**：`.venv` 是本机可重建环境，不是项目源码；应根据项目元数据和锁文件恢复解释器及依赖。

**常见误解**：认为 clone 会复制作者整台电脑的环境；认为没有 `.venv` 就说明仓库不完整。

### `.gitignore` 与已跟踪文件

**问题**：已经把文件加入 `.gitignore`，为什么 Git 仍然显示它的修改？

**参考要点**：文件此前已经进入版本历史；ignore 主要影响尚未跟踪的文件，不自动取消已有跟踪。

### Windows 与 WSL 环境

**问题**：Windows 已经安装 Python，为什么进入 WSL 后可能找不到？

**参考要点**：Windows 与 WSL 是不同用户空间，具有各自的文件系统视图、PATH、软件和项目环境。

### Ruff、Pyright 与 pytest

**问题**：三个工具分别解决什么问题？

**参考要点**：Ruff 侧重格式和静态代码规则；Pyright 进行静态类型分析；pytest 运行测试验证实际行为。三者不能互相完全替代。

### 损坏日志记录

**问题**：日志文件中一行无法解析，程序应该怎样处理？

**参考要点**：记录行号和可理解原因，隔离该行，继续处理后续记录；避免吞掉所有异常或使整个文件处理失败。

### 筛选组合

**问题**：同时给出 `level` 和 `source` 时应怎样处理？

**参考要点**：按照公开规则采用“且”；所有行先验证，再对合法记录筛选，非法记录不能因筛选而消失。

### Cargo 项目恢复

**问题**：clone 一个 Rust 项目后为什么通常没有 `target/`？怎样确认项目能够恢复和构建？

**参考要点**：`target/` 是本机生成的构建产物，应由 Cargo 根据源码、`Cargo.toml` 和锁文件重新生成；可以通过 check、build 或 test 核验。

### Rust 开发工具

**问题**：`cargo fmt`、`cargo check`、`cargo clippy` 和 `cargo test` 分别在检查什么？

**参考要点**：fmt 处理格式；check 执行类型检查和编译检查但不生成最终产物；Clippy 提供更高层的代码惯用法和问题提示；test 构建并运行测试。任一项通过都不能替代其他项。

### 所有权与借用

**问题**：一个函数取得 `String` 后，调用者不能继续使用原变量，可能是什么原因？

**参考要点**：所有权可能移动进函数；可以根据需求改为借用 `&str`、返回所有权或在确有需要时复制。候选人应说明选择对所有权和开销的影响。

### `Result` 与错误处理

**问题**：项目中每次遇到错误都直接 `unwrap` 有什么问题？

**参考要点**：可恢复错误会导致整个进程 panic；应根据所在边界传播、转换或向用户报告错误。`?` 可以传播兼容错误，但不等于处理了错误。

### `delay` 与异步

**问题**：为什么客户端 A 的 `delay` 不应阻塞客户端 B 的 `ping`？

**参考要点**：不同连接由独立异步任务处理，等待使用 Tokio 异步定时器；不应在 executor 上执行长时间阻塞等待。只对已经进入 Tokio 层级的候选人使用本题。

### 使用参考程序定位项目问题

**问题**：自己的客户端无法与自己的服务端通信，怎样使用参考程序定位？

**参考要点**：分别用参考服务端测试自己的客户端，再用参考客户端测试自己的服务端，通过替换一端缩小问题范围。

本题作为项目追问，不作为固定的底层网络知识题。

## 命令行实操

使用预先准备的临时目录或小 Git 仓库，控制在 5–8 分钟。允许使用候选人熟悉的 shell 和命令自身的 `--help`，不允许联网搜索或使用 AI。

任务包括：

1. 判断当前目录。
2. 查看目录内容并找到 README。
3. 查看 README 内容。
4. 查看 Git 状态和最近历史。
5. 修改一个普通文本文件。
6. 展示修改产生的差异。
7. 根据 README 运行一条已知测试或检查命令。

准备至少两个等价版本。评委评价对操作结果的理解，不评价打字速度、特定命令写法或 shell 技巧。
